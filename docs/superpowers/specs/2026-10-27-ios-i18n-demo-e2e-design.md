# Sunbay Checkout iOS SDK — i18n, Example App & E2E Automation (Design)

> Status: design, pending implementation plan
> Date: 2026-10-27
> Scope: three coordinated additions to the iOS SDK repo — (1) an internationalization
> subsystem in the SDK, (2) a real Xcode Example app generated by Tuist, and (3) a
> protocol-driven end-to-end test target. This document is the agreed design brief
> produced during brainstorming.
> Convention: written in English per AGENTS.md §2 (all repo docs are English).

---

## 0. Background & intent

The SDK currently has **no localization**: `CheckoutConfiguration.locale` exists but is
never consumed, and every user-visible string in `PaymentSheetViewController` is a
hardcoded English literal (`"Cancel"`, `"Saved cards"`, `"New card"`, `"Save this card"`,
`"Pay"`, `"Apple Pay"`). There are no `.strings`/`.xcstrings` resources and no SwiftPM
resource bundle.

The repo ships two SwiftPM executable example targets today. `SunbayCheckoutDemo` is a
SwiftUI app, but as a bare SwiftPM executable it has **no Info.plist / entitlements**, so
real-device Apple Pay cannot run and it cannot be driven by UI automation.
`ApplePayProbe` is a standalone PassKit probe independent of the SDK. Testing today is
host-side XCTest only — there is **no UI automation and no e2e harness**.

This work delivers:

1. **i18n subsystem** — `en-US` + `zh-CN` for v1, structured so adding languages (and, later,
   host-supplied custom languages) is cheap and low-risk.
2. **Example app** — a real Xcode app (Tuist-generated) with a Stripe-style configuration
   playground, used as customer-facing reference code and for our own subjective verification
   and the manual real-device Apple Pay gate.
3. **E2E automation** — a pure, protocol-driven XCTest target (the iOS counterpart of the
   jssdk e2e), running on `swift test` with no real app and no XCUITest.

### Decisions locked during brainstorming

- **Language codes use BCP-47 region form** (`en-US`, `zh-CN`, `zh-TW`), unified with hpp /
  jssdk. v1 ships `en-US` + `zh-CN` only.
- **Chinese variant**: Simplified only (`zh-CN`) for v1.
- **Example app**: a real Xcode `.xcodeproj` **generated by Tuist** (declarative `Project.swift`
  checked in; generated project git-ignored).
- **E2E scope**: drive the **Core protocol boundary only** (decision "B"). A PaymentSheet UI
  driver seam (decision "A") is recorded as v-next.

### Alignment with the sibling web SDK

The web checkout SDK treats `locale` as an opaque passthrough string with resolution order
*integrator option → session language → default*, never translates client-side, keeps errors
**code-based** with server-supplied human text, and passes **raw amount + ISO currency code**
with formatting deferred. This design mirrors that policy while adopting Stripe iOS's native
on-device mechanism (per-bundle `Localizable.strings` + a localized-string helper).

## 1. i18n subsystem (SDK core)

Goal: replace hardcoded literals with a localizable, extensible, UI-test-free structure.

### 1.1 Resource layout & SwiftPM exposure

```
Sources/SunbayCheckout/Resources/Localizations/
  en.lproj/Localizable.strings
  zh-Hans.lproj/Localizable.strings
```

- `Package.swift`: set `defaultLocalization: "en"`; add `resources: [.process("Resources/Localizations")]`
  to the `SunbayCheckout` target so SwiftPM compiles the `.lproj` dirs into `Bundle.module`.
- `.lproj` directory names use Apple's native identifiers (`en`, `zh-Hans`) because iOS bundle
  resolution expects them. The **public API** uses the BCP-47 region form (`en-US`, `zh-CN`);
  an internal mapping bridges the two (see §1.3).

### 1.2 Localized-string helper (internal)

```swift
// internal, not public API
func SunbayLocalizedString(_ key: String, _ comment: String) -> String
```

- Thin wrapper that ultimately calls `bundle.localizedString(forKey:value:table:)`, where
  `bundle` is chosen by the resolved target language (§1.3).
- Migrate current literals to keys. Key convention: `sunbay.<area>.<meaning>` (lowercase,
  dot-separated), which is itself extension-friendly. Initial keys:
  - `sunbay.sheet.cancel`
  - `sunbay.sheet.savedCards`
  - `sunbay.sheet.newCard`
  - `sunbay.sheet.saveThisCard`
  - `sunbay.sheet.pay`
  - `sunbay.sheet.applePay`

### 1.3 Language resolution chain (core extension point)

An internal `LocalizationResolver` with a single responsibility: map an *external language code*
to the *bundle used to look up strings*. Order:

1. `CheckoutConfiguration.locale` (explicit, region form e.g. `zh-CN`)
2. Session-delivered language (when the backend session carries one)
3. System language (`Locale.preferredLanguages`)
4. Fallback `en-US`

- Maintains an internal map **external code → `.lproj` dir name**: `en-US → en`, `zh-CN → zh-Hans`.
  Adding a language = one map entry + one `.lproj` dir, with zero change to resolution logic.
- Unmatched external codes fall back BCP-47 style from specific to general (`zh-CN` → `zh`),
  ultimately to `en-US`.

### 1.4 Seam for future host-supplied / full custom languages (v1: not implemented, recorded)

- `SunbayLocalizedString` runs a **two-tier lookup**: *host-supplied table (empty in v1) → SDK
  built-in bundle*. v1 exposes **no public API** to inject a host table, but the call sites already
  route through both tiers, so adding the API later changes no call site.
- This directly anticipates the hpp/jssdk roadmap toward host-defined full custom languages.

### 1.5 Error message localization

- `CheckoutError` keeps its code/category shape unchanged (no public API break; consistent with
  the web contract).
- Add an internal `code → localized message` map (via `SunbayLocalizedString`) to produce a
  user-visible string when the server supplies none; pass server-supplied text through when present.
- The raw error payload is still **never logged** (AGENTS.md §2.3 unchanged).

### 1.6 Amount / currency formatting

- Add an internal `AmountFormatter`: input `Amount` (raw number + ISO currency code) + resolved
  locale, output a localized currency string via `NumberFormatter` (`.currency`). Called at render
  time; the core holds only the raw number.

## 2. Example app (real Xcode app, Tuist-generated)

### 2.1 Project generation

- Directory `Example/SunbayCheckoutDemo/`, with a declarative `Project.swift` (Tuist) checked in.
  The generated `.xcodeproj` is **not** checked in (added to `.gitignore`; produced by `tuist generate`).
- One app target `SunbayCheckoutDemo` depending on the local SDK package; real `Info.plist`,
  **Apple Pay entitlement** (`com.apple.developer.in-app-payments`), placeholder merchant id (the
  real merchant id lives in the developer's Apple account, never in the repo — AGENTS.md §5).

### 2.2 Configuration playground (home screen)

- SwiftUI home screen; configuration carried by a `DemoSettings` struct (`Codable` / `Equatable`):
  environment (test/prod), locale (`en-US` / `zh-CN`), currency + amount, enabled methods
  (card / applePay / savedCard), COF toggle, appearance, and the existing scenario script
  (succeeded / failed / pending / requiresAction / timeout).
- "Pay" assembles a `CheckoutConfiguration` from `DemoSettings` + injects mock services, presents the
  real `PaymentSheet` / `ApplePayButton`, and shows the `CheckoutOutcome` at the bottom.
- Existing `DemoApp.swift` / `MockDemoBackend.swift` logic carries over, generalized to be configurable.

### 2.3 Role

- Customer style reference + our subjective verification + the manual real-device Apple Pay gate.
  **Does not** carry automated assertions.
- The standalone `ApplePayProbe`'s real-device role is absorbed by this app. Recommendation: **keep**
  the probe as a minimal, SDK-independent pure-PassKit isolation check, documenting the relationship
  between the two.

## 3. E2E automation test target (protocol-driven — decision B)

### 3.1 Target

- Add `Tests/SunbayCheckoutE2ETests/` as a **separate XCTest target** (separation of concerns),
  running on `swift test` (host). No simulator, no XCUITest.

### 3.2 Case shape (iOS counterpart of the jssdk e2e)

Each case = (config/`DemoSettings` + scripted backend responses + scripted actions) → assert the
`CheckoutOutcome` terminal state + key side effects:

- Upgrade existing `MockPaymentService` / `MockCofService` to be **scriptable** (return
  succeeded / failed / pending / requiresAction per scenario; `submit` throws to simulate
  timeout → unknown).
- Drive the **Core protocol boundary**: `confirmNewCard` / `confirmSavedCard` / `confirmWallet`
  → `authorize → confirm → poll → outcome`, bypassing the PaymentSheet UI action layer.
- Coverage: the five outcomes; idempotency / dedup; timeout recovery (`retrievePayment`); COF
  one-tap single use; **localization assertions** (`zh-CN` vs `en-US` resolve the correct
  user-visible / error strings).

### 3.3 v-next (recorded, not in v1)

- Decision "A": a PaymentSheet UI driver seam that makes in-sheet branches (saved-card selection,
  cancel) e2e-drivable without a real app. Until then, those UI branches are covered by existing UI
  unit tests + Example app subjective verification.

---

## 4. Future extensions (recorded, out of v1 scope)

- **More languages**: add `.lproj` + one resolver map entry each (e.g. `zh-TW → zh-Hant`). No logic
  change.
- **Host-supplied / full custom languages**: expose the §1.4 two-tier lookup's first tier as public
  API so integrators can inject or override strings, mirroring the hpp/jssdk roadmap.
- **UI driver seam for e2e** (decision A, §3.3).
- **Localized-layout snapshot tests** (e.g. RTL / long-string screenshots), if desired later.

---

## 5. Impact & constraints checklist

- Public API: `CheckoutConfiguration.locale` becomes live; `CheckoutError` shape unchanged.
- Sensitive-data boundary (AGENTS.md §2, §6): localization touches only static chrome and
  code-derived error text — never card data, tokens, COF secrets, or the RSA payload. Nothing new
  is logged or persisted.
- Core stays UI-agnostic (AGENTS.md §6): the resolver / formatter are pure logic; the string helper
  is used by the UI layer.
- Backend contract remains behind protocols (AGENTS.md §7): scriptable mocks live in tests only.
- Git/secrets (AGENTS.md §5): no merchant certs/keys; placeholder merchant id only; generated
  `.xcodeproj` git-ignored.
