# SunbayCheckout - Example app

A **mock-backed** demo of the SunbayCheckout iOS SDK, shipped as a real Xcode app generated by
[Tuist](https://tuist.dev). It consumes only the SDK's **public API** (`SunbayCheckout`,
`PaymentSheet`, `ApplePayButton`, `CheckoutOutcome`, `CheckoutError`) plus the public
`SunbayCheckoutTestSupport` doubles (`ScriptablePaymentService`, `ScriptableCofService`,
`DemoSessionFactory`, `DemoRSAKey`) - no internal types, no `@testable`, no real backend, and no
secrets.

## Generate & build

The app is declared by a checked-in Tuist manifest (`Project.swift`) plus Swift sources under
`Sources/`. The generated `.xcodeproj` / `.xcworkspace` are **not** committed (see the repo
`.gitignore`); regenerate them with Tuist:

```bash
# from Example/SunbayCheckoutDemo
tuist generate            # produces SunbayCheckoutDemo.xcworkspace + .xcodeproj
```

Then build/run on a simulator (pick any installed iOS Simulator device):

```bash
xcodebuild \
  -workspace SunbayCheckoutDemo.xcworkspace \
  -scheme SunbayCheckoutDemo \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  build
```

Or open the generated workspace in Xcode and run the `SunbayCheckoutDemo` scheme (Cmd-R).

The manifest declares `SunbayCheckoutDemo` as the single runnable app scheme and disables Tuist's
automatic per-target scheme generation (`options: .options(automaticSchemesOptions: .disabled)`), so
this is the only app scheme you select. (Xcode may still list extra schemes that Xcode itself
auto-exposes for the local Swift package dependency, e.g. `SunbayCheckout` / `SunbayCheckout-Package`
- those are not the app and are not needed to run the demo.)

The manifest wires the SDK as a **local Swift package** at the repo root
(`packages: [.package(path: "../..")]`) and depends on the `SunbayCheckout` and
`SunbayCheckoutTestSupport` products by name. `tuist generate` resolves the package into the project.

## Running on a real device (Apple Pay signing)

The simulator needs no signing, and by default the manifest ships a **placeholder** Apple Pay
merchant id (`merchant.com.sunbay.demo`) and **no** signing team, so it commits clean and runs on
the simulator with zero setup. That placeholder is not registered with Apple, so building for a
**real device** will fail to sign with errors like *"doesn't support merchant.com.sunbay.demo
Merchant Identifier"* and *"doesn't include the com.apple.developer.in-app-payments entitlement"*.

To sign for a real device, override the merchant id (and your team) via Tuist environment variables
at generate time - these are read by the manifest's `Environment` API and never committed:

```bash
# from Example/SunbayCheckoutDemo
TUIST_SUNBAY_DEMO_MERCHANT_ID=merchant.com.<your-merchant> \
TUIST_SUNBAY_DEMO_DEVELOPMENT_TEAM=<YOUR_TEAM_ID> \
  tuist generate
```

The merchant id must already be registered under that team in your Apple Developer account, with
the Apple Pay capability enabled. For the full token path on-device you also need a sandbox tester
signed in and a test card in Wallet. Running `tuist generate` with no overrides restores the
placeholder.

## Configuration playground

The app is a Stripe-style config screen (`DemoRootView`) over a `DemoSettings` value. Every knob
maps into a `CheckoutConfiguration` plus scripted mock services at Pay time:

- **Environment** - `test` / `production` (maps to `CheckoutConfiguration.environment`).
- **Locale** - `en-US` / `zh-CN` (maps to `CheckoutConfiguration.locale`). **This drives SDK UI
  localization at runtime** (see below).
- **Amount** - currency code + minor units (maps to the scripted `CheckoutSession.amount`).
- **Payment methods** - toggles for Card / Apple Pay / Saved card (maps to the session `methods`).
- **COF enabled** - whether saved cards are offered (maps to session `cofEnabled`; when on, the
  sheet lists the mock saved cards for one-tap pay, and a `customerAccessSecret` is passed).
- **Scenario** - scripts the mock `submit` result across the five outcomes: `succeeded`,
  `failed`, `pending`, `requiresAction`, and `networkTimeout -> unknown` (the mock throws on
  `submit`, so Core resolves to `unknown(sessionId:)` and would recover via `retrievePayment()`
  then `getResult`).

Below the knobs:

- **PaymentSheet (L1 black-box)** - a "Pay (sheet)" button constructs
  `PaymentSheet(checkout:sessionId:customerAccessSecret:)` and calls `present(from:)`. The sheet
  renders the new-card form + "Save this card", the mock saved cards (when COF is on), and an
  Apple Pay entry row. The returned `CheckoutOutcome` is shown in "Last outcome".
- **Standalone ApplePayButton (L3)** - placed directly on the screen, with `onResult` and
  `onAvailabilityChange` wired. This is the working wallet path: tapping it drives
  `authorize -> confirmWallet` end-to-end.

## Localization verification gate

Switching the **Locale** picker to `zh-CN` and presenting the PaymentSheet re-localizes the SDK's
own UI strings - a reviewer should see the pay / cancel sheet titles rendered in Chinese. The app
hand-writes **no** Chinese string literals; the configured `CheckoutConfiguration.locale` flows into
the SDK, whose bundled `.strings` provide the localized titles. This app is the UI localization
verification surface.

## In-sheet Apple Pay (known v-next wiring item)

The Apple Pay **row inside the PaymentSheet** is currently a cancel-only placeholder in the SDK
(wiring it to real wallet authorization would require changing SDK internals, out of scope here).
**The working wallet path in this release is the standalone `ApplePayButton`**, which drives
`confirmWallet` end-to-end and is fully exercised by this app.

## Apple Pay on device

The Tuist manifest sets a placeholder Apple Pay entitlement
(`com.apple.developer.in-app-payments = ["merchant.com.sunbay.demo"]`). Real in-app Apple Pay on a
device requires the integrating developer to substitute their **own** merchant id and provision the
matching merchant capability/certificate in their Apple Developer account. No real merchant
certificates or secrets are committed (see AGENTS.md section 5).

## The demo RSA key

`SunbayCheckoutTestSupport.DemoRSAKey` embeds a **throwaway demo RSA public key** (PKCS#1 DER, base64).
It is a **public key** (not a secret), generated once so the SDK's `CardEncryptor` can import it and
produce valid ciphertext. The matching private key was discarded and never committed - no real
backend can decrypt with it. **Do not** use this key in a real integration; the real public key is
delivered by the backend via the session.

## Relationship to ApplePayProbe

`Example/ApplePayProbe/` is a separate, **SDK-independent pure-PassKit probe**: it links PassKit
directly and does **not** depend on SunbayCheckout. It exists to verify the Apple Pay capability ->
wallet sheet -> token path on a real device without any backend. This Tuist app, by contrast, is the
**SDK-consuming** real-device/demo surface - it exercises the SDK's public API end-to-end against the
mock services.
