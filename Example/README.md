# SunbayCheckout - Example app

> **DEV ONLY.** `Example/DevServer` holds merchant API credentials. In production, create the session in YOUR backend; never put the API key in an app.

A demo of the SunbayCheckout iOS SDK, shipped as a real Xcode app generated by
[Tuist](https://tuist.dev). It consumes only the SDK's **public API** (`SunbayCheckout`,
`PaymentSheet`, `ApplePayButton`, `CheckoutOutcome`, `CheckoutError`) plus `DevSessionClient` from
`SunbayCheckoutTestSupport` - no internal types, no `@testable`, and no secrets in the app.
The app is real-only: every payment creates a real order through the session server at the URL you enter
and pays against the SDK environment you pick (**Pay > Order > More**: Dev by default, Test, Prod). The
server decides which credentials are used, so point it at one that holds credentials for the same environment.
There is no mock mode.

## Run flow

Configure and start the dev server first, then run the app:

```bash
cd Example/DevServer && cp .env.example .env.local
# fill in .env.local (git-ignored) with your sandbox credentials, then:
node server.mjs
```

The default server URL is `http://127.0.0.1:8095` (editable in the app). The Example enables
`NSAllowsLocalNetworking` for this; the SDK itself needs no ATS exception.

**Real device:** the phone cannot reach `127.0.0.1` on your Mac. Start the server with `HOST=0.0.0.0`
(for example `HOST=0.0.0.0 node server.mjs`) and enter the Mac's LAN address as the server URL.
Caution: `HOST=0.0.0.0` exposes an unauthenticated, credential-backed endpoint on your LAN (see `Example/DevServer/.env.example`); use it only on a trusted network.

**Production integration.** Your host app fetches the session from its own backend and hands it to the SDK:

```swift
// Your backend creates the session (API key stays server-side) and returns this JSON:
// { "sessionId": "...", "checkoutClientSecret": "ccs_...", "customerAccessSecret": "cas_..."? }
let s = try await myBackend.createCheckoutSession(orderId: order.id)

let checkout = SunbayCheckout(configuration: CheckoutConfiguration(environment: .production))
let sheet = PaymentSheet(
    checkout: checkout,
    sessionId: s.sessionId,
    customerAccessSecret: s.customerAccessSecret,
    checkoutClientSecret: s.checkoutClientSecret
)
let outcome = await sheet.present(from: viewController)
```

Apple Pay needs a real device. Real new-card and Apple Pay payments have not been verified by the
Example; see `docs/real-api-integration-checklist.md`.

## Card on file switches

The settings screen has two toggles. They feed `CheckoutConfiguration(cardOnFile:)`:

- **Card on file enabled** (default on): `CardOnFileOptions.isEnabled`. Turn it off to hide saved cards
  and the save checkbox. It can only disable COF; the session must also allow it.
- **Pre-tick save card** (default off): `CardOnFileOptions.saveByDefault`. Only sets the checkbox's
  initial state; the card is saved only if the checkbox is on at submit. Saving a card needs a billing address: keep "Requires billing address" on (Pay > Order, on by default) or "Pass a host billing address" (see Address collection).

The saved-card list comes from the backend.

## Generate & build

The app is declared by a checked-in Tuist manifest (`Project.swift`) plus Swift sources under
`Sources/`. The generated `.xcodeproj` / `.xcworkspace` are **not** committed (see the repo
`.gitignore`); regenerate them with Tuist:

```bash
# from Example/SunbayCheckoutDemo
tuist generate            # produces SunbayCheckoutDemo.xcworkspace + .xcodeproj
```

Then build/run on a simulator (pick any installed iOS Simulator device):

```bash
xcodebuild \
  -workspace SunbayCheckoutDemo.xcworkspace \
  -scheme SunbayCheckoutDemo \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  build
```

Or open the generated workspace in Xcode and run the `SunbayCheckoutDemo` scheme (Cmd-R).

The manifest declares `SunbayCheckoutDemo` as the single runnable app scheme and disables Tuist's
automatic per-target scheme generation (`options: .options(automaticSchemesOptions: .disabled)`), so
this is the only app scheme you select. (Xcode may still list extra schemes that Xcode itself
auto-exposes for the local Swift package dependency, e.g. `SunbayCheckout` / `SunbayCheckout-Package`
- those are not the app and are not needed to run the demo.)

The manifest wires the SDK as a **local Swift package** at the repo root
(`packages: [.package(path: "../..")]`) and depends on the `SunbayCheckout` and
`SunbayCheckoutTestSupport` products by name. `tuist generate` resolves the package into the project.

## Running on a real device (Apple Pay signing)

The simulator needs no signing, and by default the manifest ships a **placeholder** Apple Pay
merchant id (`merchant.com.example.yourapp`) and **no** signing team, so it commits clean and runs on
the simulator with zero setup. That placeholder is not registered with Apple, so building for a
**real device** will fail to sign with errors like *"doesn't support merchant.com.example.yourapp
Merchant Identifier"* and *"doesn't include the com.apple.developer.in-app-payments entitlement"*.

**Integrators:** use your **own** merchant id, registered in your Apple Developer account. The
manifest writes it to both the entitlement and Info.plist (`SunbayDemoMerchantId`); the app reads it
from there for `CheckoutConfiguration.applePayMerchantId`, so the entitlement and the SDK
configuration always match.

**Sunbay engineers:** the internal test merchant `merchant.native.com.sunbay.dev` is for Sunbay's own testing
and demos only; pass it through the same variable (with the internal team id) instead of
committing it as a default.

To sign for a real device, override the merchant id (and your team) via Tuist environment variables
at generate time - these are read by the manifest's `Environment` API and never committed:

```bash
# from Example/SunbayCheckoutDemo
TUIST_SUNBAY_DEMO_MERCHANT_ID=merchant.com.<your-merchant> \
TUIST_SUNBAY_DEMO_DEVELOPMENT_TEAM=<YOUR_TEAM_ID> \
  tuist generate
```

The merchant id must already be registered under that team in your Apple Developer account, with
the Apple Pay capability enabled. For the full token path on-device you also need a sandbox tester
signed in and a test card in Wallet. Running `tuist generate` with no overrides restores the
placeholder.

## Configuration playground

The app is a four-tab config screen (`DemoRootView`) over a `DemoSettings` value: **Pay** (session, order, the pay actions),
**Look** (themes, effects, locale), **Options** (payment methods, addresses, saved cards) and
**Logs** (live output), ordered by how often they are used. Every knob
maps into a `CheckoutConfiguration` (environment from Pay > Order > More, default `.dev`) or the dev-session request at Pay time:

- **Server URL** - base URL of the local dev session server.
- **Locale** - `en-US` / `zh-CN` (maps to `CheckoutConfiguration.locale`). **This drives SDK UI
  localization at runtime** (see below).
- **Appearance / Color scheme** - presets and light/dark override (maps to `Appearance`).
- **Address collection** - billing and shipping pickers: Automatic (follow session, default) / Simple /
  Full / Off. Automatic shows the full backend-layout form when the session flag is on and hides the
  section otherwise; Simple, Full and Off ignore the session flag. Country and region data come from
  the real HPP address API.
  - **Order requires billing address** / **Order requires shipping address** - send
    `collectBillingAddress` / `collectShippingAddress` to the dev server (independent of the pickers).
  - **Pass a host billing address** / **Pass a host shipping address** - pass a fixed, complete US test
    address (San Jose, CA; the shipping one has names and a phone) to
    `PaymentSheet(billingAddress:shippingAddress:)`. A host address is used only when the session collects
    that kind and the address is complete; with Automatic the form for that kind is then hidden. A form that
    is shown wins over the host address.
- **Payment methods** - **Apple Pay button text** sets `Appearance.applePayButtonType` (the sheet's express row)
  and `ApplePayButton(type:)` (the embedded button); the default `.plain` shows the logo only. **Hide Apple Pay** / **Hide Card** build `CheckoutConfiguration.paymentMethodFilter`
  (`PaymentMethodFilter(hide:)`). Hiding Card also hides saved cards; hiding both makes `present` fail with
  `NO_PAYMENT_METHOD_AVAILABLE`.
- **Amount** - USD only; minor units (default 105 = 1.05). Sent to the dev server as major units.
- **Card on file** - the two switches above.

Pay tab:

- **Order** - amount, "Requires billing / shipping address" (billing on by default) and "Supports saved cards" (the session's
  card-on-file flag), plus a collapsed **More** group with the SDK environment and the session server URL
  (rarely changed). Set these first, then **Session** ("Create session") creates an order through the
  session server using them. Changing any of these, or a payment that reaches a final state (succeeded, pending, unknown), discards the session; the payment actions stay disabled until one exists. Section notes are behind the "?" next to each title.
- **PaymentSheet (L1 black-box)** - "Pay (sheet)" constructs
  `PaymentSheet(checkout:sessionId:customerAccessSecret:checkoutClientSecret:)` for the session and calls
  `present(from:)`.
- **Embedded components** - nothing is rendered until you tap "Load ApplePayButton"; it then shows an
  `ApplePayButton` (L3) bound to the session's `sessionId` and `checkoutClientSecret`, with `onResult` and
  `onAvailabilityChange` wired. "Remove" unloads it. Needs a real device for the wallet sheet.
- **Result toast** - every payment result (succeeded, canceled, failed with its code, pending, unknown)
  from the sheet or the embedded button is also shown as a toast.

Logs tab: a live, newest-first log of session creation, sheet states, outcomes and every event delivered
through `SunbayCheckout.onDiagnostic` (code, ignored names and reason only, never address values). Lines are
also printed to the Xcode console with a `[SunbayDemo]` prefix. "Copy" puts the log on the clipboard and
"Clear" empties it. Secrets and card data are never logged.

## Localization verification gate

Switching the **Locale** picker to `zh-CN` and presenting the PaymentSheet re-localizes the SDK's
own UI strings - a reviewer should see the pay / cancel sheet titles rendered in Chinese. The app
hand-writes **no** Chinese string literals; the configured `CheckoutConfiguration.locale` flows into
the SDK, whose bundled `.strings` provide the localized titles. This app is the UI localization
verification surface.

## Apple Pay in the sheet and standalone

Both the Apple Pay row inside the PaymentSheet and the standalone `ApplePayButton` authorize through the
same wallet path: the request is built from the session's `ewalletParam`, contacts are requested only when
the session collects an address that the host did not supply, and the returned addresses are submitted with
the payment. Use the "Hide Apple Pay" toggle to exercise `paymentMethodFilter`. Real-device behavior is
tracked in `docs/real-api-integration-checklist.md`.

## Apple Pay on device

The Tuist manifest sets a placeholder Apple Pay entitlement
(`com.apple.developer.in-app-payments = ["merchant.com.example.yourapp"]`). Real in-app Apple Pay on a
device requires the integrating developer to substitute their **own** merchant id and provision the
matching merchant capability/certificate in their Apple Developer account. No real merchant
certificates or secrets are committed (see AGENTS.md section 5).

## Relationship to ApplePayProbe

`Example/ApplePayProbe/` is a separate, **SDK-independent pure-PassKit probe**: it links PassKit
directly and does **not** depend on SunbayCheckout. It exists to verify the Apple Pay capability ->
wallet sheet -> token path on a real device without any backend. This Tuist app, by contrast, is the
**SDK-consuming** real-device/demo surface - it exercises the SDK's public API end-to-end against the
Dev backend.
